# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Preflight — several sessions work on this repo at once

Before your first edit, always:

1. `git rev-parse --show-toplevel`. If it is the main checkout (`D:/Repositorio/web-coparena`), **stop and open a worktree**: `npm run rama -- feature/<nombre-corto>`. A directory inside `.worktrees/` with **no `.git` file is not a worktree** — git walks up and writes into the main checkout instead.
2. `npm run ramas:limpiar` (reports only): who else is working and on what. If a worktree already covers your task, ask instead of guessing.
3. Say in your first message which worktree, which branch and which port slot you took.

Everything else is in «Git workflow» at the end of this file. Read it before working around it.

## Project

Astro 5 site for "La Copa Arena", a beach volleyball event at Playa O Pozo (Porto do Son). All content is in Spanish. Deployed to Cloudflare Pages (build command `npm run build`, output directory `dist`). The site output is static; a backend scaffold exists as Cloudflare Pages Functions + D1 (see Backend below).

## Commands

- `npm run rama -- feature/<nombre>` — opens the branch **and its worktree**, installs, and assigns a port slot. The way to start any work (see Git workflow)
- `npm run integrar -- -m "…"` — merges `development` in, runs `verify`, and publishes the branch to `development` without checking it out anywhere
- `npm run ramas:limpiar` — reports leftover worktrees, orphan directories and merged branches (`--aplicar` to act)
- `npm run dev` — dev server at 127.0.0.1
- `npm run build` — runs `astro check` (TypeScript/type checking) then `astro build`, then builds the worker
- `npm test` — unit + integration tests (no build needed, ~10 s). The everyday command.
- `npm run verify` — build + test types + **all** tests including e2e. The gate before merging to `development` (see Tests below)
- `npm run preview` — serve the built `dist/`
- `npx wrangler d1 migrations apply DB --local` — apply D1 migrations to the local database
- `npx wrangler dev --port 8788` — serve the built site plus `functions/` with the local D1/R2 bindings (run `npm run build` first). **Not** `wrangler pages dev`: the project is a Worker with static assets (`main = ".worker/index.js"` + `[assets]` in wrangler.toml), not a Pages project.

## Architecture

- Static output (`output: "static"`, directory-format URLs in [astro.config.mjs](astro.config.mjs)). No frameworks, no islands — plain `.astro` components only.
- All styling for the **public site** lives in a single stylesheet, [src/styles/global.css](src/styles/global.css), imported once by `BaseLayout`. Components do not use scoped `<style>` blocks; add new styles to global.css using the existing CSS custom properties (`--sea`, `--cream`, `--lime`, `--coral`, `--dune`, `--pine`, `--dusk`, etc.) defined in `:root`.
- **Exception — the admin panel.** `/admin/*` styles live in [src/styles/admin/](src/styles/admin/), split by responsibility (`tokens`, `layout`, `tables`, `forms`, `dialog`, `ediciones`, `torneo`) and pulled in by `index.css`, which `AdminLayout` imports after global.css. The panel is noindex and admin-only, so its dense table CSS is not served to public visitors. Its own tokens (`--adm-*`) hang off `body.is-admin`, **not** off `.admin-app`: the `<dialog>`s mount outside the shell (`showModal()` won't open a dialog with a `[hidden]` ancestor) and would otherwise render with no surface colour.
- Display typography is Titan One (npm package `@fontsource/titan-one`, imported by `BaseLayout`), exposed as `--font-display` and used for h1/h2, the giant hero dates and the nav "Inscribirse" sticker button. It echoes the rounded chunky lettering of the Copa Arena logo; headings are Title Case (no uppercase transform). Body text stays Inter/system.
- Two layouts: `BaseLayout.astro` (HTML shell, meta, fonts, global CSS, and the three site-wide scripts) and `LegalLayout.astro` (wraps BaseLayout with header/footer and hero for the legal pages `aviso-legal`, `cookies`, `privacidad`).
- Editable event content (dates, claim, contact, social links, location/"Dónde estamos" data, perks) is centralized in [src/data/event.ts](src/data/event.ts) rather than hardcoded in pages. Real socials come from the Copa Arena linktree (https://linktr.ee/la.copa.arena).
- **`event.phases` is copy, and nothing ties it to the real calendar.** The Hero, the portada CTA, `/torneo/premios/` and the JSON-LD `SportsEvent` all derive from it, but what `/torneo/` actually paints comes from `partidos` in D1 through `/api/torneo`. They drifted: the site announced «31 Jul - 2 Ago» and «7 Ago - 9 Ago» while no match was scheduled on either the 31st or the 7th, so the portada promised a Friday the tournament never had. Move the calendar and you must come back here by hand — the only lock is remembering.
- The landing is a vertical journey: hero with the watercolor action photo (`copa-arena-hero-watercolor.png`) under a cream overlay (the hero location eyebrow links to `/donde-estamos/`) → "Pasos para apuntarse" (`#torneo`): comic speech bubbles zigzagging like a chat (`pasos` in event.ts; colors cycle sun/coral/lime/aqua via `--paso-bg`, hover lifts / `:active` sinks) → "¡Tienes que venir!" perks on a sand band → pine forest divider → sunset CTA band with SVG scenery. The header is left-to-right: brand wordmark (Titan One, `--deep`, distinct from the Inter nav links), nav links, and the tilted "Inscribirse" sticker CTA (`.header-join`, coral→sun gradient, wiggle keyframes gated on `html.js`).
- `/donde-estamos/` ([src/pages/donde-estamos.astro](src/pages/donde-estamos.astro)) is its own page (legal-page pattern): Google Maps satellite embed of Praia do Pozo/Langaño (`/maps/embed?pb=` format — the old `output=embed` endpoint now 404s) in an ink-border card + a tilted photo "postal" (Wikimedia Commons, CC0) + address/how-to-arrive list, all from the `donde` export in event.ts. The Monte Louro silhouette in `SceneHorizon` and the small `header-peak` SVG poking out of the nav pill both trace the angular mountain of the Copa Arena logo — keep their geometry in sync with the logo if it changes. Scenery components:
  - [src/components/SceneHorizon.astro](src/components/SceneHorizon.astro) — sky, sun, Monte Louro silhouette, sea, dunes. Props: `variant` (`"morning"` | `"sunset"`, recolors via CSS variables) and `dunes` (boolean). Layers carry `data-parallax="<factor>"` inside a `data-scene` container.
  - [src/components/SceneForest.astro](src/components/SceneForest.astro) — two-layer pine treeline generated deterministically in frontmatter.
  - [src/components/SandDivider.astro](src/components/SandDivider.astro) — wavy sand edge divider (props `fill`, `flip`).
  - [src/components/VideoCard.astro](src/components/VideoCard.astro) — vertical 9:16 video card, **currently unused**: reserved for action clips (pending Higgsfield credits); `.video-strip` CSS and the play/pause observer already exist.
- Client-side interactivity (cursor blob, hover states, scroll parallax for `[data-parallax]`, `.reveal` intersection reveals, video autoplay observer) is a plain script at [public/assets/site-interactions.js](public/assets/site-interactions.js), loaded with `<script is:inline ... defer>` from `index.astro`. It is not processed by Astro's bundler. It adds the `js` class to `<html>`; reveal/entrance styles are gated on `html.js` so content stays visible without JS. Everything motion-related is disabled under `prefers-reduced-motion`.

## Backend (Cloudflare Pages Functions + D1)

- The site stays static; Cloudflare Pages automatically deploys [functions/](functions/) as Pages Functions alongside `dist/`. No Astro adapter.
- [wrangler.toml](wrangler.toml) declares the `DB` D1 binding (`copa-arena-db`) and the `FOTOS` R2 binding (`copa-arena-fotos`, private player photos). The real `database_id` must be pasted after running `npx wrangler d1 create copa-arena-db` (see README).
- Migrations live in [db/migrations/](db/migrations/) (`migrations_dir` in wrangler.toml). Main tables: `equipos`, `jugadores` (0002), `estadisticas` and `jugador_atributos` (0009); `equipos.capitan_jugador_id` (0011) replaced `owner_user_id`. Only the captain's phone and email are mandatory; a non-captain player's phone is stored as `''` (never `NULL` — the column stays `NOT NULL` because rebuilding the table would drag `estadisticas` and `jugador_atributos` down with it through their `ON DELETE CASCADE`), and the API translates `''` to `null` on the way out. The first version's tables (`inscripciones`, `reservas`, created in 0001) were dropped in 0008 — don't reintroduce them. Uniqueness is enforced via normalized columns (lowercase, accent-stripped in the endpoint — SQLite NOCASE is ASCII-only) plus UNIQUE indexes.
- **`equipos.siglas` (migration 0028) is nullable, with no backfill: `NULL` means "derive from the name."** `functions/_lib/siglas.ts` exports `derivarSiglas(nombre)` — initials if they reach 3 letters (capped at 4), otherwise the first 3 letters of the first significant word; connectors (`de do da del la el los las os as y e`) don't count. **It never auto-disambiguates**: siglas that changed by themselves the day a similar team registered would be worse than a collision, because nobody would see them change — that is what the editable column is for.
- **Player uniqueness is per edición** (migration 0010): full name, phone and email can't repeat *within* an edición, but the same person re-registers freely the next year — that's what makes the per-edición history on `/jugadores/` possible at all. Every duplicate pre-check (`api/equipos.ts buscarDuplicados`, `_lib/equipos.ts buscarDuplicadosEdicion`, `api/admin/jugadores.ts buscarDuplicados`) takes the edición it must look in; when moving a player between teams, it's the **destination** team's edición. Team name (`equipos.nombre_normalizado`) is still globally unique — it's a column constraint, and the alta resolves the new team by that name.
- **`estadisticas` is one row per player per match, and it cannot be anything else.** Since migration 0012 `partido_id` is `NOT NULL`: a figure typed by hand, with no match behind it, is not representable in the database. That is the whole point — the guarantee doesn't depend on any endpoint. Everything read is `SUM(...)` over a player's rows, and `partidosJugados` is **not a column**: it is counted with `COUNT(DISTINCT partido_id)`, so it can't desync from the rows that hold it up. The edición is **not** duplicated in the table: it comes from `jugadores.edicion_id` through the join, so moving someone between teams can't desync it either. Metric names live once, in `_lib/estadisticas.ts`: `METRICAS` is the list that gets displayed (seven, `partidosJugados` flagged `derivada`). `players-list.js` repeats it by hand and `paridad-validacion.test.ts` is the lock; its `RANKING` deliberately leaves out both `saquesFallados` and `errores`, because crowning whoever fails most is not a ranking. `PATCH /api/admin/estadisticas?jugador=N` **ignores** anything sent under `estadisticas`; it only saves attributes and album visibility. What *does* write the figures is the live scoring log — see «Anotación en directo» below. They are never typed: they are derived from `partido_eventos`.
- **A player's own traits live on the player row, not on the Google account.** `apodo`, `dorsal`, `posicion`, `mano`, `lema` and `nivel` are columns of `jugadores` (migration 0023); the 1–99 attributes are `jugador_atributos`, keyed by player. All of it therefore belongs to a player *in an edición*: the organisation can fill in the card of someone who never logged in, and 2025's ficha keeps the position they played in 2025. What stays on the account (`perfiles`) is only `avatar_key`. The dividing line is **traits go with the player; accumulated figures (points, spikes…) stay in `estadisticas`**.
- `PATCH /api/perfil` writes the ficha onto the player row of the **current edición only** — rewriting past ediciones would falsify the history — and answers **409** when the account is in no roster at all, because there is then nowhere to write. It ignores `atributos` **and `nivel`**: those two are the organisation's, and `nivel` now lives in the very row that PATCH updates, which is exactly when a stray `SET nivel = ?` sneaks in.
- **Migration 0023 deliberately did not drop the old `perfiles` columns; [0024](db/migrations/0024_perfiles_sin_ficha.sql) does**, one deploy later, because migrations are applied *before* the new code ships and dropping them in the same jump would have left the old code — still serving traffic — selecting columns that no longer existed. Same lesson as `is_admin`. `perfiles` now holds only `avatar_key`, which is genuinely the account's and is what `tieneFoto` and the `?foto=N` fallback rest on.
- **0024 re-runs the transfer before dropping, and refuses to drop when data would be left behind.** Between 0023 applying and the new code shipping, the old code could still write fichas into `perfiles`; that would be stranded. So 0024 first backfills again with `COALESCE(j.col, p.col)` — filling only what's still empty, so a value the organisation has since set from the panel is never overwritten — and then runs a guard: `CREATE TABLE _cerrojo_ficha (huerfanas INTEGER NOT NULL CHECK (huerfanas = 0))` fed by the count of `perfiles` rows that still carry ficha data and have **no** `jugadores` row to receive it. A non-zero count violates the CHECK and D1 aborts the whole file with nothing dropped. A loud failed deploy beats silent data loss; the fix is to register that person (or note their ficha) and re-run.
- [functions/api/equipos.ts](functions/api/equipos.ts) is the real registration endpoint: `POST /api/equipos` (multipart: `payload` JSON + optional `foto_0..n`; Turnstile check, validation with per-field Spanish errors keyed `jugadores.<i>.<campo>`, R2 photo upload, transactional `DB.batch` insert, confirmation email) and `GET /api/equipos` (public list: team names + player count only, for privacy). Shared helpers live in [functions/_lib/](functions/_lib/) (`http`, `validacion`, `turnstile`, `gmail`) — `_lib` files don't become routes. Client validation mirrors `functions/_lib/validacion.ts` by hand across **four** scripts that each load with `<script is:inline>` and can't import from the server: [public/assets/team-form.js](public/assets/team-form.js) (`/inscripcion/`), [public/assets/my-team.js](public/assets/my-team.js) (`/mi-equipo/`), [public/assets/admin/equipos.js](public/assets/admin/equipos.js) (roster editor) and [public/assets/admin/jugadores.js](public/assets/admin/jugadores.js) (single-player create/edit). Keep all four in sync — `test/unit/paridad-validacion.test.ts` fails if any of them drift, from the server or from each other.
- Confirmation email is sent from copa.arena.2000@gmail.com via Gmail API OAuth (plain-text MIME). Secrets: `TURNSTILE_SECRET_KEY`, `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` (production: `wrangler pages secret put`; local: `.dev.vars`, gitignored). Email failure never rolls back a registration (201 with `emailEnviado: false`).
- Frontend pages: `/inscripcion/` (form, dynamic player cards, min 2 players + subs up to 15, RGPD consent, Turnstile widget — site key in `src/data/event.ts` `inscripcion.turnstileSiteKey`, currently the always-passing test key), `/equipos/` (client-side fetch list) and `/jugadores/` (the public album). The old `POST /api/inscripciones` endpoint was **removed**: it was the only write in the whole API with no session behind it, and nothing called it.
- **`[data-auth-logged-out]` is the whole site's door, not `/inscripcion/`'s.** The same card carries the Google button on `/mi-equipo/`, `/camisetas/`, `AdminLayout` and `AnotadorLayout`. Gating it on `inscripcionesAbiertas` (commit `cdda8a2`) therefore removed the login from all of them the moment the edición closed registrations: Mi zona showed nothing between the intro and the footer, and the scorer lost its door on tournament day, which is exactly when registrations are already closed. What genuinely depends on them being open is marked `data-auth-solo-abiertas`; that pass only ever hides, never shows, and only `/inscripcion/`'s card asks for it. `test/unit/auth-cerradas.test.ts` covers both halves and reads the `.astro` files so the marker can't spread.
- **`/jugadores/` is the public album**, served by [functions/api/jugadores.ts](functions/api/jugadores.ts) — the second endpoint outside `functions/api/admin/`, and GET-only: `GET /api/jugadores` (current edición), `?id=N` (ficha with per-edición history, palmarés and career totals) and `?foto=N`. It never returns phone or email; the email is only used *inside* the queries to link the same person across ediciones. `jugadores.oculto_publico` takes someone out of the album (right to object) without touching their registration. The page is one file with two views, list and ficha, deep-linked with `?j=N` — same client-fetch pattern as `/equipos/`.
- The trading card is [public/assets/cromo.js](public/assets/cromo.js) (`window.CopaCromo`), shared by `/mi-equipo/` and `/jugadores/`; `cromo.js` must be loaded **before** the page script. It is a **FIFA-style card**: crown, overall rating with the position under it, portrait, name, and the six attributes in a 2×3 grid.
- **`cromo.js` owns the attribute list, and it is the only client copy.** It used to be repeated four times in client code (`players-list.js`, `perfil.js`, `admin/estadisticas.js`, `admin/usuarios.js`); now the two public pages hand `crear()` the raw `atributos` object and the card maps labels and 3-letter abbreviations, while the panel gets the list from the server. `test/unit/paridad-validacion.test.ts` compares `clave`/`etiqueta`/`abrev` against `_lib/perfil.ts` **and** asserts the page scripts never declare `ATRIBUTOS` again. `players-list.js` still repeats `METRICAS` by hand, which that same test guards.
- **The card is a collectible-card silhouette built in three slices**: `corona()` (the horned top arch), `.cromo-cuerpo` (the only slice that grows with the content, and the only one with side borders) and `punta()` (the bottom point). Slicing it is what lets a ficha with palmarés and one without measure differently without distorting the arch or the point. Each SVG fill deliberately overruns the viewBox on the seam side so the clip eats the path's closing edge and no join shows.
- **Still no `clip-path` and no `mask`, for the original reason**: both clip the ink border and the hard offset shadow, which are the whole house style. The ink edge is a stroke *inside* each SVG (`.cromo-filo`, `non-scaling-stroke` so the big card and the album mini carry the same 3px), and the shadow is `filter: drop-shadow(10px 10px 0 var(--ink))` on the card — **not** `box-shadow`, which would draw the shadow of a rectangle the card no longer is and spill out past the point.
- **The tiers are bronce/plata/oro, and the outer silhouette is identical in all three** — that's what makes it read as a set. What differs is `.cromo-skyline`, the relief inside the arch: the site's own skyline rising with the metal (dune, Monte Louro, Monte Louro with its summit, the same angle as the logo and `SceneHorizon`). It carries a real load — bronce and oro are both warm and colour alone doesn't separate them — so `test/unit/album-jugadores.test.ts` asserts the skyline path differs per tier *and* that the outline path doesn't.
- **Two sets of metal variables, and they are not interchangeable.** `--metal-{oro,plata,bronce}-{claro,oscuro}` (two stops) stay as they were: the palmarés medals and the ranking podium use them, and two stops are enough there. The card uses `--cromo-{oro,plata,bronce}-{alto,medio,bajo}` (three stops) — with two the gradient goes flat and stops reading as metal. Retuning the card must not move the podium, which is why they were split instead of widened.
- **Each card mints its own `<linearGradient>` id** (a counter in `cromo.js`). Share one and every card in the album grid paints with the first card's metal — a bug invisible in any test that mounts a single card, so there's one that mounts three.
- **The overall rating is never stored.** `mediaAtributos` in `_lib/perfil.ts` averages the **rated** attributes (not all six — rating only two apartados must not sink someone to a third of their worth) and returns `null` when there are none, so the card comes out with no figure rather than a zero. Same reason standings aren't stored: a saved average would start lying the moment an old attribute is corrected. The album listing returns `nivel` + `media` but **not** the six raw attributes: the grid paints metal and rating without a request per player, and the breakdown is one tap away in the ficha.
- `astro dev` does not serve `/api`; test the full flow with `npm run build` + `npx wrangler dev --port 8788`.

## Admin panel (`/admin/*`)

- One page per entity under [src/pages/admin/](src/pages/admin/) (`index`, `equipos`, `jugadores`, `estadisticas`, `camisetas`, `usuarios`, `roles`, `torneo`, `ediciones`), all on [src/layouts/AdminLayout.astro](src/layouts/AdminLayout.astro): fixed sidebar, page header, and the shared auth gate. Add a section by creating the page, its script, and an entry in the layout's `secciones` array — **with its `permiso`**, which is what decides whether the sidebar shows it.
- **`/admin/estadisticas/` does not edit figures.** It shows them summed from the player's matches, read-only, and edits what the organisation really does set by hand: the 1–99 attributes, the card tier and whether the person appears in the public album. The rating it displays is the one the GET returns, never recomputed in the client — that would mean a second copy of `mediaAtributos`.
- **The card is split across two panel pages on purpose.** Identity (apodo, dorsal, posición, mano, lema) goes in `/admin/jugadores/`, which is already the person-by-person page; the valuation (attributes + tier) goes in `/admin/estadisticas/`, which is already where the organisation rates people. `/admin/usuarios/` edits **nothing** about the card: it used to paint six attribute inputs the server silently discarded, and that dead path is gone.
- Backend is one file per entity under [functions/api/admin/](functions/api/admin/) (`index` = summary, plus `equipos`, `jugadores`, `estadisticas`, `camisetas`, `ediciones`, `fotos`, `roles`, `torneo`). Actions that aren't plain CRUD go in a `?accion=` query param (`equipos?accion=posicion`, `equipos?accion=ficha`, `jugadores?accion=normalizar-nombres`). Every export starts with `requirePermiso(request, env, "<recurso>.<accion>")`; shared helpers are in `_lib/admin.ts` (`jsonAdmin`, `idDeQuery`, `mapJugador`…) and `_lib/fotos.ts` (R2: `subirFoto`, `limpiarFotos`, `servirFoto`).
- **Two ways to belong to a team, only one of them authorizes writes.** `equipoDeUsuario` matches any player row carrying your email — but that email is typed by whoever registered the team, with no confirmation from its owner. So `GET /api/mi-equipo` uses it (any listed player sees the roster, with `puedeEditar: false`), while `PATCH`/`DELETE` go through `equipoDelCapitan`, which only matches the team's **captain** (`equipos.capitan_jugador_id` → the player row whose email is yours). The captain is the only player whose phone and email are mandatory, and the only one who can hand the team over — by designating another player as captain. A team created from the admin panel has no captain until one is set, and until then nobody can edit it from `/mi-equipo/`.
- **`_lib/equipo-editor.ts` is the only place a team roster gets written.** It diffs by player `id` — updating in place, deleting what's missing, inserting what's new — so `foto_key` survives an edit. Both `PATCH /api/admin/equipos` and `PATCH /api/mi-equipo` go through it, and any client that saves a roster **must send each player's `id`**; without it the player is treated as new and the old row (with its photo) is deleted.
- **Its `UPDATE` deliberately does not mention the cromo columns** (`apodo`, `dorsal`, `posicion`, `mano`, `lema`, `nivel`), so they survive a roster save. That is a fragile invariant: add `apodo = ?` to that statement and saving the roster from `/mi-equipo/` wipes the whole team's cards, done by their own captain, with nobody in the organisation noticing. `test/integration/cromo-jugador.test.ts` is the lock.
- **`PATCH /api/mi-equipo` blocks ceding the captaincy through the back door.** Changing the current captain's *own* email in the same save that keeps them as captain would hand the team to whoever owns that new address, without the explicit "designate someone else" step. So the endpoint only treats a save as a handover when the submitted captain is a **different** player row; if it's still the same one (`nuevoCapitan.id === currentTeam.capitan_jugador_id`), their email must stay the session's own or the save is rejected with 400 ("Para ceder el equipo, designa a otro capitán."). A captain slot filled by a brand-new row (no `id` yet — someone just added to the roster in this same save) always counts as a genuine handover, since it can never match the current captain's id.
- `/admin/equipos/` works the whole roster at once; `/admin/jugadores/` works person by person (standalone create, edit, move between teams). They cross-link: `/admin/jugadores/?equipo=N` arrives filtered.
- Client JS is one IIFE per page in [public/assets/admin/](public/assets/admin/), all on top of `core.js`, which exposes `window.CopaAdmin`: `api()`/`apiJson()` (throw an `Error` carrying `.campos` and `.status`), `onReady()`/`recargar()` for the load cycle, `tabla()` for the data table, and `confirmar()` for destructive dialogs. Don't use `window.confirm`.
- The payload key for the team editor is **`equipo`**, not `nombre` — that's what `validarRegistro` in `_lib/validacion.ts` reads, same as `/inscripcion/` and `/mi-equipo/`.
- **`siglas` travels as a loose multipart field in the team editor, not inside `payload`.** That JSON goes through `validarRegistro`, shared with `/inscripcion/` and `/mi-equipo/` and bound by the four-script parity test — a field there would land in the public registration form. Absent means "don't touch"; empty means "clear it, derive again" (see `equipos.siglas` in Backend). `GET /api/admin` also had to start returning it: it feeds the table's edit button, and without it reopening the editor showed the field blank over a correct database.
- **`/api/partidos` is the one endpoint that lives outside `functions/api/admin/`** (the public board reads it). Only its `GET` is public; `POST`/`PATCH`/`DELETE` all go through `requireAdmin`. Writes never fall back to `localStorage` — a save that doesn't reach D1 must surface as an error — but reads still do, so the bracket stays visible at the beach with no coverage.
- **The bracket is always the current edición's, and everything that reads or wipes in bulk must say so.** `listarPartidos`, `sortearDesdeDb`, `reemplazarPartidos` (the `draw` action) and `DELETE ?todos=1` all filter on the `EDICION_ACTUAL` fragment in [functions/api/partidos.ts](functions/api/partidos.ts). They didn't, and the two bulk deletes ran `DELETE FROM partidos` unqualified: redrawing one year's bracket wiped every previous year's matches and, through the `ON DELETE CASCADE` on `estadisticas.partido_id`, the whole statistical history with them. Operating on a single partido by id (`PATCH`, `DELETE ?id=`) stays unfiltered on purpose — correcting an old result is legitimate; mass-deleting one is not.
- `/admin/torneo/` carries **two** IIFEs, and that is deliberate: [torneo-formato.js](public/assets/admin/torneo-formato.js) decides what the tournament *is* (phases, groups, rules, standings) and [torneo.js](public/assets/admin/torneo.js) runs what is being *played* (loose draw, schedule, live scoreboard). Both sit on `core.js` like every other panel script.
- **`camisetas_reservas.entregada` (migración 0031) es un booleano, y la asimetría es el diseño.** La organización la marca y la desmarca desde `/admin/camisetas/`; su dueño ya no puede borrar la reserva desde `/camisetas/` (409 en el `DELETE`, no sólo el botón escondido: la pantalla se puede saltar), porque el registro es lo que le deja en su historial qué compró y en qué edición — de ahí que `GET /api/camisetas` empezara a devolver también el año. Va en `?accion=entrega` y no como un campo más del `PATCH` normal: aquél valida nombre, talla y cantidad, así que marcar una entrega obligaría a reenviar la reserva entera desde un botón de una fila. Y el `UPDATE` de la edición **no menciona la columna**, igual que `_lib/equipo-editor.ts` no menciona las del cromo: si se añade ahí, corregir una talla deshace la entrega sin que nadie lo vea. `test/integration/camisetas-entrega.test.ts` es el cerrojo. En la fila es una casilla (`.admin-toggle`, subida a `tables.css` desde `ediciones.css`, que ya tenía la misma) y no un botón, porque la etiqueta alternando cambiaba de ancho y movía «Editar» y «Borrar» entre dos clics.
- **There is no legacy section any more.** `/admin/heredado/`, `GET /api/admin/heredado` and the `inscripciones` / `reservas` tables were removed (migration 0008) once production confirmed both tables were empty. `camisetas_reservas` (0004) is a different, live table — don't confuse it with the old `reservas`.
- **Three photo routes, two audiences.** `GET /api/admin/fotos?jugador=N` serves the player photo to the admin panel behind `requireAdmin` with `no-store`. `GET /api/equipos?foto=N` serves the team group photo (`equipos.foto_key`, migration 0007) publicly with `public, max-age=300`, on `/equipos/` and `/mi-equipo/`. `GET /api/jugadores?foto=N` serves the **same player image publicly** for the album: registration photo first, Mi zona avatar as fallback — the `/inscripcion/` and `/privacidad/` consent already covers publishing participants' photos on the web. Either way the API exposes `tieneFoto`, never the R2 key.

## «Ver como» (impersonation)

- An admin can browse the whole site as any user. The real session (`copa_session`) is never touched; a second signed cookie (`copa_ver_como`, 30 min) carries `{adminUid, targetUid}`, and `getAuthContext` in [functions/_lib/auth.ts](functions/_lib/auth.ts) resolves the *effective* user from it. It honours the cookie only after re-checking in the DB that the real user still holds `usuarios.ver_como`, so taking that permission away kills an active impersonation on the next request and a copied cookie is worthless on its own. Impersonation is a **permission, not a rank**: a reduced role that carries `usuarios.ver_como` can do it, and an admin-like role without it cannot.
- **It is strictly read-only, and that is enforced in exactly one place**: [functions/_middleware.ts](functions/_middleware.ts) rejects every non-GET/HEAD/OPTIONS request with 403 while the cookie is present. Don't add per-endpoint checks — the single choke point is the point. The whitelist (`EXCEPCIONES`) holds exactly three path+method pairs, all of which act on the *session itself* rather than on anybody's data: `DELETE /api/admin/ver-como` (leaving the mode, validated against the **real** admin), `POST /api/auth/logout` and `POST /api/auth/google`. The last two matter because logout and login are POSTs: without them a forgotten impersonation cookie left the browser unable to log out *or* back in until it expired. Logout and login both clear `copa_ver_como`.
- `GET /api/me` exposes `verComo`; `auth.js` paints the fixed warning band declared in `BaseLayout` on every page and adds `html.ver-como`. The band sits at the bottom because the site header is a `fixed` pill with its own backdrop.
- A user's role is set from `/admin/usuarios/`. Three guards in the endpoint: nobody takes the `admin` role off themselves, the last `admin` can't be demoted (getting back in would need `wrangler d1` by hand), and **nobody can hand out a permission they don't have themselves** — without that last one, delegating `usuarios.editar` would be delegating total access, since you could just give yourself a better role.

## Torneo (fases, grupos y cuadro)

- A tournament is **phases** (`torneo_fases`, either `grupos` or `eliminatoria`), a group phase holds **groups** (`torneo_grupos`), and a group holds teams (`torneo_grupo_equipos`). Migrations 0015–0017. `partidos` gained `fase_id`, `grupo_id`, `ronda_orden`, `posicion`, the progression links and `reglas`.
- **Match rules are data, not literals.** `functions/_lib/reglas.ts` owns them; the inheritance is **group > phase > defaults**, which is what lets a group of three play a single set while a group of five plays best-of-three *inside the same phase*. `normalizarReglas` never throws: unreadable JSON falls back to the defaults, because a match with no readable rules can't be refereed but must not take the bracket page down with it.
- **`partidos.reglas` is a frozen snapshot, not a pointer to the phase.** Changing the format mid-tournament must not rewrite how already-played matches were refereed — same instinct as the denormalized `equipo_a_nombre`. `test/integration/torneo-admin.test.ts` asserts it.
- **Standings are never stored.** `functions/_lib/clasificacion.ts` computes them from finished matches on every read. Storing them would mean keeping them in sync, and correcting an old scoreline would leave a table that lies. The head-to-head tiebreak is **recursive over the tied subgroup**, not pairwise: with three teams tied, A beats B, B beats C and C beats A is a real possibility and pairwise comparison produces a cycle.
- **`torneo_grupo_equipos.retirado` (migración 0033) es la única condición de la clasificación que no sale de los partidos.** Un equipo puede clasificarse y no poder jugar la fase siguiente: eso es una baja, no un resultado, así que se guarda. La alternativa —sacarlo del grupo— reescribía la clasificación de todos los que jugaron contra él. La tabla **no lo mueve de sitio**: conserva la `posicion` que se ganó en el campo y sale en gris con una cruz (`clasifica: "retirado"`). Lo que cambia es el reparto de plazas: `calcularClasificados` cuenta por **orden dentro de la lista sin retirados** y no por `posicion`, que es lo que hace que saltarse al segundo le pase la plaza al tercero en vez de dejarla vacía. `GrupoParaClasificar.retirados` es **obligatorio** y `CondicionClasificado` se enumera a mano en vez de con `Exclude`: con las dos cosas al revés, un retirado entraba en `semillas` y acababa colocado en el cuadro sin un solo error de compilación. Se marca desde `/admin/torneo/` con `PATCH ?accion=retirado&id=<grupo>`, en su propia acción y con el `UPDATE` de `editarGrupo` sin mencionar la columna, igual que `camisetas_reservas.entregada`. `test/integration/torneo-admin.test.ts` y `test/unit/clasificados.test.ts` son los cerrojos.
- **El aviso de `/torneo/` (`avisoTorneo` en event.ts) es copia, y va en el marcado estático.** Cuenta con palabras lo que la columna `retirado` hace con los colores. Está en `index.astro` y no en `torneo-page.js` porque explica una tabla que pinta JavaScript: mudado al script desaparecería justo cuando `/api/torneo` falla y no hay tabla que explicar. Lleva los nombres de los equipos escritos a mano, así que renombrar un equipo obliga a volver aquí — `test/unit/torneo-aviso.test.ts` fija el sitio, no el texto.
- **Progression runs through one function**, `propagarResultado`, called from *all three* paths that leave a match `finished`: `action:"finish"`, the point that closes the last set, and a manual `PATCH`. It's idempotent and it **never overwrites a slot marked `origen_equipo_* = 'manual'`** — that flag is what stops the bracket from silently undoing a hand-made correction.
- **A bracket is inserted last round first.** `siguiente_partido_id` is a self-referencing foreign key, so inserting a semifinal before its final points at a row that doesn't exist yet and D1 rejects it. Links only ever point forward, so reverse order always finds its target already in place.
- `renderBracket` in `public/assets/match-utils.js` now **draws from the data** and returns `false` when there are no bracket matches (a league is not a tree). It used to take the first eight matches in the list and fabricate semifinals and a final that existed nowhere — with twelve teams, or with a group phase, it showed a bracket that wasn't the tournament's.

## Público: `/torneo/` y el directo

- **`/competicion/` ya no existe.** Premios y reglas viven en `/torneo/premios/` y el cuadro real en `/torneo/`; `public/_redirects` emite un **301** de la URL vieja. Ese fichero funciona con Workers + `[assets]` (verificado con `wrangler dev`), lo cual importa porque `run_worker_first = ["/api/*"]` deja `/competicion/` fuera del worker: no hay forma de redirigir desde código.
- **`/torneo/premios/` explica cómo se puntúa la fase de grupos, y esa explicación es copia.** Los valores viven en `puntuacion`, de [src/data/event.ts](src/data/event.ts), igual que `event.phases`: quien manda de verdad es `torneo_fases.reglas` / `torneo_grupos.reglas` en D1, editable desde `/admin/torneo/`. Cambiar el baremo allí obliga a volver aquí a mano. Lo que sí se comprueba es que la copia coincida con `REGLAS_POR_DEFECTO` de `_lib/reglas.ts` (3 / 2 / 1 / 0 y el orden de los desempates), que es de donde salieron las reglas de la fase — `test/unit/puntuacion-publica.test.ts`. Se descartó leerlo de `/api/torneo`: es la lectura pesada, y la página no hace hoy ninguna petición. El grupo C juega a un set y puntúa 3 / 0, así que lleva su línea aparte; sin ella la tabla mentiría para uno de los tres grupos.
- **La tabla de puntuación es 2×2 porque ése es el hecho**: {ganas, pierdes} × {en dos sets, en tres}. El tinte de las casillas es una sola rampa de `--lime` guiada por `data-puntos`, así que la diagonal se ve — el 1 de perder en el tercero queda teñido justo al lado del 0. `table-layout: fixed` toma los anchos de la **primera** fila, de ahí que la esquina vacía (`.puntos-esquina`) sea quien lleva el ancho de la columna de etiquetas y quien se queda sin filo ni sombra; con el ancho puesto en `th[scope="row"]` la esquina se pintaba como una pegatina vacía y se comía 195px. Su `em` cuelga de la misma medida de letra que la etiqueta, no de la del `td`: medido, «Pierdes» en Titan One son 63,8px a 360 y caben en los 4,8em (73px) que deja el bloque de 560.
- **Dos endpoints públicos, con papeles opuestos.** `GET /api/torneo` es la lectura pesada (fases, grupos, clasificaciones, cuadro): se cachea 30 s con `stale-while-revalidate` y **no se sondea**. `GET /api/directo` es minúsculo y es el que sondea todo el mundo a la vez. Sondear el pesado agotaría la cuota de peticiones de Cloudflare en una tarde para releer una tabla que casi nunca cambia.
- **El presupuesto de peticiones es una decisión de diseño, no un detalle.** Con ~100 espectadores y una jornada de seis horas, el plan gratuito da para una petición por espectador cada ~22 s. De ahí que: la cadencia la mande el **servidor** (`ajustes.directo_sondeo_ms`, editable en caliente desde el panel — es la válvula del día del torneo); con la pestaña oculta no se sondee nada; fuera de `/torneo/` se vaya despacio; y tras un error haya backoff. `test/unit/directo-sondeo.test.ts` es ese presupuesto escrito como tests.
- **El ETag no ahorra peticiones.** Un 304 cuenta igual que un 200: ahorra ancho de banda y lecturas de D1. Lo único que ahorra invocaciones es sondear menos. La versión se calcula antes que el cuerpo, con una fila agregada, y lleva el marcador sumado además de `updated_at` porque dos escrituras en el mismo milisegundo darían la misma marca.
- **El botón del directo son dos elementos, no uno deshabilitado**: un `<a>` deshabilitado no existe en HTML y seguiría siendo enfocable. Encendido es un enlace que enseña **las siglas de quien juega** (`OST–PUL`), no el marcador ni la palabra «directo»: sin saber de quién, un «12–9» no informa de nada, y el marcador está a un toque en `/directo/`. El `aria-label` tampoco lo lleva, y por una razón aparte: el enlace tiene `aria-live="polite"`, así que con los puntos dentro un lector de pantalla cantaba **cada punto del partido desde cualquier página del sitio**; con siglas se anuncia una vez por partido y dice algo útil. Las siglas salen de `equipos.siglas` y, si está vacío, se derivan del nombre congelado del partido con `_lib/siglas.ts` — así que siempre hay una, y desaparece el caso especial de «antes del primer punto el marcador no dice nada». Nunca se desempatan solas: unas siglas que cambiaran el día que se inscribe un equipo parecido serían peores que un choque, porque nadie las vería cambiar — para eso está el campo editable a mano en el panel. Apagado dice «Offline» y es un `<details>` con un bocadillo dentro que cuenta que por ahí se seguirán los partidos: apagado, el hueco no se explica solo. Es `<details>` y no un `<button>` con su JavaScript por lo mismo que el menú móvil y el desplegable de «Torneo» —abre y cierra sin JS—, y lleva `data-nav-drop`, que es lo único que hace falta para que `header.js` le añada cerrarse al pulsar fuera y con Escape. `pintarBoton` lo cierra al encenderse: si no, el recado reaparecería abierto al terminar el partido.
- **El bocadillo del apagado cuelga alineado al borde derecho del chip, así que crece hacia la izquierda.** En móvil el chip está a media pantalla y `overflow-x: clip` del `<html>` le cortaría el contorno, de ahí el `max-width: min(272px, 54vw)`. Y el aire que lo separa de «Mi zona» (`.header-directo-wrap`) va **solo** en el bloque de escritorio: en móvil el vecino es el botón de menú y a 360px esos 24px se comen la palabra «Menú».
- **A 360px la cabecera ya iba justa antes de las siglas.** Medido: con el marcador antiguo («18–14») «Menú» ya asomaba ~11px fuera de la ventana; la marca y el menú no ceden más (logo y texto fijos, «Menú» es su propia decisión). Las siglas («OST–PUL», más anchas) se compensan en `@media (max-width: 560px)` encogiendo solo el chip — gap, relleno y tamaño de letra, nunca la llama — hasta dejarlo del ancho del marcador antiguo; el sobrante queda en ~12px, la misma holgura que ya faltaba, no una regresión de esta tarea. Esa regla va **después** de `.header-directo.is-vivo` sin media query en la hoja: mismo selector, misma especificidad, y a empate gana quien viene detrás — colocada en el bloque de media queries de más arriba (antes en el fichero) quedaba sin efecto a cualquier ancho.
- **`auth.js`, `header.js` y `directo.js` van ANTES del `<slot/>` en `BaseLayout`.** Los `defer` se ejecutan en orden de documento y los scripts de cada página salen dentro del slot: puestos después, `directo.js` arrancaba más tarde que el script de `/torneo/`, que se lo encontraba sin definir. Por eso `torneo-page.js` lee `window.CopaDirecto` **sin `?.`** — con encadenamiento opcional la página se quedaba sin marcador en silencio y todo lo demás parecía correcto.
- `cargarTorneo` vive en `functions/_lib/torneo-vista.ts` y la comparten el panel y la página pública, para que la clasificación que ve la organización y la que ve el público no puedan divergir.
- **El directo es su propia página, `/directo/`, y enseña un solo partido**: hay una sola pista. `/torneo/` perdió su panel y se queda con el cuadro; lo que conserva es la suscripción a `CopaDirecto`, porque `cerroAlguno` es lo **único** que puede cambiar una clasificación y por tanto lo único que justifica releer `/api/torneo`. Sin `mirandoDeCerca`, así que sondea despacio. El chip de la cabecera apunta a `/directo/`, y una página nueva se da de alta en **tres** sitios a mano: `publicPages` de `src/data/seo.ts`, `navItems` de `SiteHeader.astro` y la lista de `SiteFooter.astro`.
- **La página del directo no pide `/api/torneo`.** Quien entra solo a mirar el marcador no paga la lectura pesada del sitio; es media razón de que sea página aparte.
- **Dos endpoints otra vez, y por lo mismo.** `GET /api/directo` sigue siendo lo sondeado y **no cambia de URL**: gana `enPista` (ids), `feed` (los últimos 30 apuntes con claves de una letra) y `feedTotal`, sin un solo nombre. Los nombres, dorsales, metales y notas van en `GET /api/plantilla?partido=ID` (`functions/api/plantilla.ts`), que se pide **una vez por partido** y se cachea 300 s. Endpoint propio y no un `?plantilla=` dentro del directo porque son dos políticas de caché opuestas dentro del handler que no puede fallar.
- **El feed es una ventana completa, no un incremento.** Un delta («dame lo posterior a X») no sabe expresar una corrección ni un deshacer: el marcador retrocedería y el espectador se quedaría con el punto borrado en pantalla. Quien evita repintar es el cliente, que reconcilia por clave (`e:orden` / `c:id`); por eso también `directo-sondeo.test.ts` sigue verde **sin tocarlo**, que es la prueba de que el presupuesto sobrevivió al rediseño.
- **`partidos.log_version` (migración 0027) es lo que hace que el ETag no mienta.** `versionDirecto` agregaba solo `partidos`, así que fijar una alineación, registrar un cambio de jugador o anotar un bloqueo que no puntúa **no movían la versión**: el espectador recibía un 304 con el cuerpo viejo, el marcador congelado, sin error y sin nada que lo dijera. La alternativa —un `COUNT(*)` sobre `partido_eventos`— encarecía justo el camino barato (el 304 pasaría de leer una fila a leer el log entero: D1 factura filas leídas). El contador lo sube `sentenciaLogVersion` desde un único sitio.
- **`oculto_publico` no filtra la fila en el directo: la proyecta.** Quien pidió no salir del álbum sigue en pista y el marcador tiene que cuadrar, así que sale — por su dorsal, sin nombre, sin nota y sin foto (`/api/jugadores?foto=N` le responde 404, así que `tieneFoto: false` evita gastar una petición en un fallo seguro). Conserva su metal, que no dice quién es. Nunca por sus iniciales: dentro de un equipo de cuatro identifican tanto como el nombre. En `/api/anotacion` **no** se aplica nada de esto: quien anota tiene que ver a quién atribuye el punto.
- **Lo que viaja en el cuerpo y no está en la versión se congela en el navegador.** `versionDirecto` agrega además los `ajustes` y el próximo partido programado (por su `id` y su `updated_at`, no por su ronda ni por los nombres). Sin nadie jugando la versión era siempre la misma —«0 partidos, 0 puntos»—, así que todo el que ya la tuviera recibía **304 para siempre**: subir la cadencia desde el panel, que es la válvula de la cuota, no llegaba a nadie, y mover la hora del primer partido tampoco. Justo la mañana del torneo, cuando aún no ha empezado nada. Sigue siendo una sola consulta.
- **La versión acaba en una cabecera HTTP, así que es ASCII y punto.** Un nombre de equipo dentro —«Ría», «Ñ»— y el navegador tira un `TypeError` al leer la respuesta: el directo entero caído, y por una tilde. De ahí que el próximo partido entre por `id`+`updated_at` y que `etagDe` escape (no limpie: sustituir por «_» juntaría dos versiones distintas y devolvería un 304 con el cuerpo viejo). `test/integration/directo-version.test.ts` lo comprueba con equipos acentuados.
- **`/api/plantilla` no se reintenta en cada sondeo cuando falla.** El guardia de «ya la tengo de este partido» solo se ponía al recibirla bien, así que un 500 o un corte de red dejaban a `directo-page.js` pidiéndola en **cada** sondeo: el gasto de cada espectador se dobla justo el día que algo va mal. Ahora hay una espera de 30 s atada al id del partido, para que empezar otro pida el suyo sin esperar. `test/unit/directo-page.test.ts`.
- **Las siglas viajan en el marcador, y entran en la versión en `hex()` con delimitador.** `GET /api/directo` sirve `teams.A.siglas`/`.B.siglas` resolviendo en JS —`equipos.siglas || derivarSiglas(nombre congelado del partido)`, no un `COALESCE` de SQL— el nombre congelado, la misma razón por la que el cuadro lo pinta así, y lo que hace legible un hueco que todavía dice «Ganador SF1». Tenían que entrar en `versionDirecto` o corregir unas siglas durante el torneo no le llegaría a **nadie** —todos seguirían con su 304 y el cuerpo viejo—, el mismo fallo que ya documentan los ajustes y el próximo partido. Van en `hex()` porque la versión acaba en una cabecera HTTP y una tilde ahí tira un `TypeError` que se lleva el directo entero. Y la concatenación lleva **delimitador** (`GROUP_CONCAT(s, '|')`, no `''`): en hexadecimal cada byte son dos caracteres sin separador, así que dos repartos distintos de las mismas letras colisionan — «ABC»+«D» y «AB»+«CD» dan el mismo `41424344` — y los dos caben en el rango de 2–4 caracteres del panel.
- **En `/directo/` mandan los sets, y los puntos del set van debajo.** Es el único sitio del sitio donde el número grande no es el que más cambia: los puntos se mueven en cada rally y los sets un par de veces por partido, pero lo que dice quién va ganando el partido es el segundo — y hasta ahora vivía dentro de la línea pequeña de detalle, que pasó a decir «Set 2 · a 21». Ninguno de los dos lleva rótulo: esa línea hace de leyenda y dos rótulos más costarían alto en una pantalla que se mira de pie. **`.versus-sets .versus-puntos` lleva `min-width: 0`**, y eso es lo que hace que quepa: `.versus-puntos` reserva `1.4ch` para que el tanteo no salte de ancho al pasar de 9 a 10, pero un marcador de sets no pasa de 3. Medido a 390px, ese hueco eran 42px de los 114 que pedía la fila en una columna de 83 (`minmax(72px, 26%)`), con las cifras cayendo encima de los retratos; sin él la fila mide 72. La columna no se ensancha: a 390px el retrato ya ocupa 82 de los 90 de cada mitad. De paso desaparece un desbordamiento que ya existía — el tanteo a 9vw con dos cifras por lado pedía 103px en esos mismos 83.
- **En el directo, quien regala el punto se marca en vez de celebrarse.** `cromo.fallar()` es la hermana de `vibrar()`: equis, cara triste y la foto en gris durante 5 s (y no 2, porque esto cuenta algo que el marcador no dice y quien mira desde la arena no está pendiente en ese segundo). Quién recibe cuál lo decide **`lado_punto ≠ lado_jugador`**, no el tipo, así que vale igual para el saque fallado —que hasta ahora sacudía el retrato de quien lo falló, o sea la animación de celebrar— y para cualquier tipo `aRival` que se añada. Se compara `p` con `l` y **nunca con `null`**: un `lado_punto` que existe no significa «lo ganó mi lado», que es el atajo que ya costó un Crítico. El anotador hace lo mismo leyendo `aRival` del catálogo. La marca es un solo nodo, `.retrato-fallo`, con la cara dentro: va por encima del aro —el marco es un círculo con `overflow: hidden` y le comería las puntas a la equis— pero no puede colgar del retrato con `inset: 0`, porque el retrato mide también el nombre y el apellido y la equis quedaría centrada por debajo de la cara. De ahí `--retrato-lado`, que saca a variable el `clamp` del marco para que las dos medidas no puedan separarse. La cara ocupa la esquina de abajo a la derecha —la única libre— **dentro** de la caja del marco: `.retrato` lleva `contain: layout paint` y lo que se saliera se recortaría sin avisar. Con `prefers-reduced-motion` la marca sale igual y sólo se salta la entrada: es información, no adorno.
- **`/torneo/partido/?p=ID` es cómo fue un partido, y su endpoint es el compañero de `feedPublico`.** Aquél sirve la **cola** del log a quien sondea el directo, así que no puede replegar desde el principio ni leer el log entero cien veces por minuto; `GET /api/historial?partido=ID` ([functions/api/historial.ts](functions/api/historial.ts), lógica en [_lib/historial.ts](functions/_lib/historial.ts)) se pide **una vez** al abrir un partido ya jugado y sí lo lee entero. Por eso puede decir lo que el directo no: el marcador que dejó cada línea en **cualquier** set, con el parcial completo en el punto que cierra —sale del `historial` del pliegue y no de `puntos`, que ya volvieron a cero—, y el set **derivado del pliegue** en vez de leído de `partido_eventos.set_numero`, que es la columna que existe para quien solo trae la cola. Fichero propio y no un `?historial=` dentro del directo por lo de siempre: dos políticas de caché opuestas (300 s si el partido está `finished`, 10 s si no) en el handler que no puede fallar. No devuelve **ni un nombre de jugador**: los pone el cliente desde `/api/plantilla`, que ya proyecta a quien está oculto. La página no sondea.
- **La barra de avance va casi al final del `<main>`, y eso no es maquetación: es cómo funciona `sticky`.** `position: sticky` con `bottom` sólo desplaza el elemento hacia **arriba**, así que pega a quien todavía no ha llegado por abajo y no retiene a quien ya ha pasado — colocada bajo el marcador, que es donde pedía el diseño, se despegaba al primer scroll (medido: a 1200px de scroll quedaba 442px por encima del borde). Puesta al final flota sobre toda la página y se apoya sobre el pie al llegar abajo, que es lo que `fixed` no sabe hacer. De paso el orden de tabulación queda bien. El carril y el `<input type="range">` son dos elementos superpuestos: el carril pinta un tramo por set, ancho en proporción a los puntos que costó, y el `input` pone teclado, foco y lector de pantalla, que un `div` con `pointerdown` habría costado.
- **La pista retrocede con la barra reconstruyendo la alineación hacia atrás.** Desde `enPistaFinal` se deshace cada cambio posterior al momento por su `pos` (el hueco de `partido_alineacion`). Si en ese hueco no está quien el cambio dice que entró se para y deja lo que hay: `fijarAlineacion` sobrescribe la alineación entera sin borrar los cambios, así que el desajuste es alcanzable. El resumen por jugador, en cambio, es del partido **entero** y no se mueve con la barra — recalcularlo por momento obligaría a contar puntos en el cliente, que es la regla de `lado_punto` que vive sólo en el servidor.
- **`conHistorial` no sale de `origen_marcador` ni de `log_version`.** `soltarAnotacion` devuelve el primero a `'manual'` con el log intacto, y el segundo sube también al publicar el partido o al mover el cronómetro sin que exista un solo evento: las dos columnas ofrecerían un historial vacío o esconderían uno que sí está. Sale de un `EXISTS` sobre `partido_eventos` en `cargarTorneo` — una sonda al índice de `UNIQUE(partido_id, orden)` por partido, en un endpoint cacheado 30 s que no se sondea.
- **`Versus.astro` y `partido-vista.js` son lo que impide que las dos vistas se separen.** El marcado del versus y el pintado (retratos que se mueven en vez de recrearse, las frases del historial, el trato a quien está oculto) los comparten `/directo/` y `/torneo/partido/`. Los `data-*` del componente son la interfaz: renombrar uno deja las dos pantallas mudas a la vez, y eso es deliberado. `directo-page.js` conserva lo suyo —sondeo, reconciliación por clave, reacción del retrato— porque es lo que sólo pasa en directo.
- **La banda de «estamos en directo» de la portada va en flujo, el primer elemento en flujo de `<body>`, y aparta lo fijo con `--banda-directo`.** La cabecera es una píldora `position: fixed` con su fondo también fijo — la misma razón por la que la banda de «ver como» va abajo—, así que una banda arriba las tapa si no se les hace sitio. `directo.js` **mide** el alto real de la banda al pintarla en vez de fijar un número: en móvil son dos líneas (49px en escritorio, 86px medido en móvil) y un nombre de equipo largo puede hacer tres. `.header-backdrop` cambió su `inset` a `var(--banda-directo) 0 auto 0` en vez de sumar un `top:` después, que habría sido un enlace frágil con la regla original. Es un suscriptor más del sondeo que ya corre en portada (el chip de la cabecera comparte la misma llamada), así que no cuesta ni una petición nueva ni cambia la cadencia. Muestra **nombres completos** de los equipos — el chip ya lleva las siglas.

## Anotación en directo (`/anotador/`)

- **`partido_eventos` is the source of truth for a match being scored.** `partidos.points_*`/`sets_*` and the rows in `estadisticas` are **derived** from it on every write, by `plegarEventos` plus one aggregate statement. That is what makes undo be "delete the row and fold again" instead of subtracting by hand and hoping it adds up. Migrations 0019–0021.
- **There is exactly one recompute path, including on append.** Touching only the affected player when adding, and recomputing fully when undoing, would save a handful of row-writes per point — and would leave two ways to reach the same state that one day stop agreeing. At ~40 matches of ~60 points it is ~15k row-writes a day against D1's free 100k: there is no reason to buy that risk.
- **An event carries two sides, and they are not redundant.** `lado_jugador` is whose action it was; `lado_punto` is who scores, or `null` when the rally kept going. With `tipo='saque_fallado'` they **differ** — failing gives the point to the other team, never to whoever served. `lado_punto` is computed by the server and never accepted from the client: inverting it is trivial and the damage (crossed scoreboard and stats) would not surface until the tournament is over. A non-null `lado_punto` does **not** mean "my side scored" — whoever reads the column has to compare it against `lado_jugador`, not against `null` alone; a Critical-severity review finding was exactly that shortcut.
- The invariant is **«every point has an action with a player behind it»**, not «every point adds to somebody's tally», and now also **«no action scores by its type: it scores by its `lado_punto`»** — but that second half is about `puntos` only, and the two halves must not be blurred together. A failed serve adds to `saquesFallados` for whoever served it and gives `puntos` to nobody, because `puntos` counts only the rows where `lado_punto = lado_jugador` and a failed serve's `lado_punto` is the other side. `bloqueos` and `chilenas` are counted the opposite way, on purpose: the aggregate is `SUM(CASE WHEN tipo = 'bloqueo' …)` / `'chilena'`, so **every** row of that type counts, whether or not `lado_punto` is set. A block that only kept the rally alive still lands on that player's `bloqueos` — the action happened either way, and only `puntos` asks the question the type itself can't answer.
- **El error no forzado (migración 0032) es un tipo `aRival`, no «un punto del rival».** Vuelve lo que la 0028 quitó, pero con significado: la 0028 tiró el `error` genérico porque no decía qué había pasado y por él se colaba cualquier punto sin autor. Ahora es una acción de quien la comete —su ficha la recoge— cuyo punto cruza la red, exactamente como el saque fallado. Atribuirlo a alguien del equipo que se lleva el punto le regalaría un mérito que no tuvo, que es lo único que se podía hacer sin este tipo. Se cuenta **por tipo** (`SUM(CASE WHEN tipo = 'error_no_forzado' …)`), como `bloqueos` y `chilenas`, y no por `lado_punto`: la acción ocurrió mirara donde mirara el punto. `puntos` no lo suma, porque `lado_punto ≠ lado_jugador`. La columna `estadisticas.errores` **ya existía** —una de las tres que la 0028 dejó vivas y sin leer—, así que no hizo falta migrarla; la 0032 la vacía, porque lo que arrastraba eran cifras del `error` viejo que la 0028 ya había traducido a `saque_fallado` en el log, y sacarlas al álbum sería contar dos veces lo mismo. `remates` y `defensas` siguen muertas. La migración reconstruye `partido_eventos` para ensanchar su `CHECK` (SQLite no sabe alterarlo) y por eso **se aplica entre partidos**: D1 manda el fichero como una sola consulta sin transacción.
- **Los dos tipos `aRival` van seguidos en `TIPOS` y comparten fila en la botonera.** El orden de esa lista es el orden de los botones. `.anot-btn--saque_fallado` llevaba `grid-column: 1 / -1` cuando era el único que cruzaba el punto; con dos, la fila entera son dos filas y ~76px más de alto, y el panel ya mide 742 de los 844 de un móvil. Medido: juntos, el bloque sigue en 217px (dos filas de 68). De paso el saque fallado acortó su ayuda a «Punto del rival» — la larga rompía a dos líneas a 140px de ancho.
- **`partidos.origen_marcador` is what stops the panel and the scorer from overwriting each other.** `'manual'` (the default, so nothing existing changes) means `/api/partidos` owns the score; `'eventos'` means the log does, and `/api/partidos` answers **409** to anything that touches the scoreboard while still allowing the time, the court or the round name. Without it, «scorer records a point → someone corrects by hand in the panel → scorer records another point» lost the correction silently.
- **`tipo='ajuste'` is an opening balance, not a point.** It carries no player and generates no statistics. It is the only honest way for a match that started without a scorer to gain one halfway: of those earlier points nobody knows who scored them, and they will not be invented.
- **A match kept by hand is not scored over: the server refuses the first event** (`MarcadorSinAdoptar` in `_lib/eventos.ts`, 409 carrying the flat score). The fold rewrites `partidos.points_*`, so scoring the first point on a match sitting at 8–6 with sets 1–1 turned it into 1–0 in the first set and those points were left nowhere. The two ways out are both `adoptar`: as-is, or `desdeCero: true`, which writes an `ajuste` of 0–0 — still a log entry saying who zeroed it and when, not a deletion. The guard lives in the server because the screen can be walked past: entering by URL was enough to empty the scoreboard.
- **`GET /api/anotacion` returns `marcadorPanel` (the flat columns) and `pendienteDeAdoptar` alongside the folded state.** It didn't, and the screen therefore *could not* know: folding an empty log gives 0–0, so it painted 0–0 and hid the «Adoptar» button — its condition read the folded state, so `sinLog && conMarcador` was never true and the honest path was unreachable while the destructive one was the default. While the decision is pending, `/anotador/partido/` hides the court and the thumb strip: no painting buttons that will answer 409.
- **`lado_punto` is the only thing that says whether an action scored; the catalog only says whether that has to be asked.** Each entry in `TIPOS` (`functions/_lib/marcador.ts`) carries `punto: "siempre" | "pregunta"` and `aRival: boolean`; `ladoDelPunto(tipo, ladoJugador, puntua?)` is the one function that turns those into a `Lado | null`, and it runs on the server only, never the client. `bloqueo` and `chilena` are `"pregunta"`: the type alone can't say whether that block or that dive closed the rally, so an unanswered `puntua` resolves to `null` rather than a guess. There used to be a fixed `PUNTUA` map of type → boolean the client kept for its optimistic paint («everything but defensa scores») — a copy waiting to go stale the day a type was added. It's gone: the client reads `tipo.punto` and `tipo.aRival` straight off the same catalog the server uses.
- **`/anotador/partido/` loads `match-utils.js`, and reads it without `?.`.** It didn't load it at all: `predecir` returned `null` every time (no optimistic paint, the very thing its comment block exists for) and `objetivoDelSet` fell back to `puntosPorSet`, so the decisive set announced «a 21» in a set played to 15. Nothing broke, which is why nobody noticed — `test/unit/anotador-partido.test.ts` reads the `.astro` so the order can't be lost again.
- **`.anot-cuerpo` on the auth wrapper is what makes the thumb zone reach the bottom.** `AnotadorLayout`'s `[data-auth-logged-in]` div sat between `.anot-app` and `.anot-panel` with no styles, so `flex: 1` had a block parent and `margin-top: auto` had nothing to distribute: measured 588px of empty space under the buttons on a 1200px screen.
- Two more things the screen was missing rather than getting wrong: the history lines in «Más» are buttons that open the correction dialog (`accion: "corregir"` existed from the start with no way to ask for it — the only fix was undoing every point after the mistake), and a finished match shows **sets** as the big numbers plus the set-by-set line, because the last set's close returns the points to 0–0 and a 2–1 win used to sign off as «0 – 0».
- `/anotador/` has a door: an entry in `AdminLayout`'s `secciones` gated on `partidos.anotar`. There was no link anywhere — the tool for tournament day was reachable only by typing the URL.
- **Los cambios de jugador viven en `partido_cambios` (migración 0026), no en el log de puntos.** `partido_alineacion` se sobrescribe entera, así que dice quién está en pista pero no cómo se llegó, y el historial del directo necesita lo segundo. Van en tabla propia y **no** como un `tipo` más de `partido_eventos` porque añadir un valor a aquel `CHECK` exige reconstruir la tabla, y con ella viajan el `UNIQUE(partido_id, orden)` que serializa a dos anotadores y los `ON DELETE CASCADE` de los que cuelga `estadisticas`. Un cambio no pliega, no puntúa y no genera estadísticas: `plegarEventos` y `sentenciasDerivadas` no lo mencionan.
- **`tras_orden` es el ancla en el historial**, no una clave ajena: un evento va en `(orden, 0)` y un cambio en `(tras_orden, 1, id)`, así que el cambio cae justo detrás del punto que estaba anotado cuando ocurrió — y si ese punto se deshace, el cambio sigue habiendo ocurrido. Lo calcula el servidor, como `lado_punto`, y por eso un cambio no necesita `ordenEsperado` ni puede chocar por el orden. Sí puede dar 409 por el reclamo, que es anterior y vale para toda escritura. `posicion` guarda el hueco de `partido_alineacion` que hereda quien entra: sin él, deshacer un cambio movería los retratos de sitio.
- **El gesto del cambio es el mismo de siempre**: tocar a un suplente (banquillo, retratos pequeños) abre en la **zona del pulgar** la pregunta «¿por quién entra?» con los titulares de ese lado. Y «Deshacer» es una sola tecla que decide el estado — si lo último fue un cambio, deshace el cambio: dos botones que elegir a ciegas entre punto y punto es justo lo que esta pantalla no puede permitirse. El diálogo de «Más» se queda: fijar la alineación entera es otra cosa, y **no borra los cambios**.
- **`corregirEvento` acepta a quien ya salió de pista.** El conjunto permitido es «alineación actual ∪ quien tiene eventos en este partido»: en cuanto hay un cambio, corregir «ese punto fue de Berta, no de Celia» dejaba de ser posible, que es justo cuando hace falta. Y reescribe `partido_eventos.set_numero` cuando el repliegue mueve una frontera de set, porque el historial público lee esa columna en vez de replegar (solo trae la cola del log).
- **La pista del anotador es el mismo versus que ve el público**, con `CopaCromo.retrato()` — una `<img>` y cero SVG por cara, para que dieciséis retratos animados no cuesten nada. Los colores de equipo son `--equipo-azul`/`--equipo-rojo` de `global.css`, compartidos con `/directo/`: quien anota y quien mira ven al mismo equipo del mismo color. De paso arreglan un contraste que estaba mal — `--coral` sobre la crema del anotador daba 2,54:1.
- **El alto del móvil es un presupuesto, y se gastó entero.** Con el versus, el banquillo y la botonera, el panel medía 836px y la zona del pulgar caía por debajo del borde en un móvil de 844. De ahí tres decisiones que parecen cosméticas y no lo son: el marcador ya no repite los nombres de equipo (los llevan las bandas de la pista), el número bajó a `clamp(2.8rem, 16vw, 4.4rem)` y el retrato es más pequeño aquí que en el directo. Quedó en 742 + 60 de barra.
- **`UNIQUE(partido_id, orden)` is the concurrency control.** The client sends the `ordenEsperado` it has seen; if another scorer got there first the insert is rejected and the second one gets a 409 instead of quietly overwriting.
- **El `UNIQUE` separa a dos pestañas; a dos personas las separa el reclamo.** `partidos.anotador_usuario_id` (migración 0029) dice quién lleva el partido. El `UNIQUE` sólo salta cuando dos anotadores coinciden en el mismo hueco: si se turnan sin llegar a chocar —y con una sola pista ése es el caso normal— los dos anotan el mismo partido y ninguno se entera. El reclamo se toma con la **primera escritura**, no al abrir la pantalla (entrar a mirar el marcador no echa a nadie), y con un `UPDATE ... WHERE anotador_usuario_id IS NULL`: la condición va dentro de la sentencia porque un `SELECT` seguido de un `if` no es atómico y dejaría el mismo agujero, más difícil de ver. La puerta está en **un solo sitio**, `onRequestPost` de `api/anotacion.ts` antes del `switch`, igual que el bloqueo de «ver como» vive sólo en el middleware. `soltar` libera el reclamo; `relevo` lo transfiere sin condiciones y es la única acción que se salta la puerta — una salida que puede fallar no es una salida. **No caduca**: el partido cambia de manos sólo cuando alguien lo pide, nunca por un reloj. El `ordenEsperado` que ahora exige `corregir` separa otra cosa: rechaza una corrección emitida desde una pantalla que no ha visto los puntos anotados después de cargarla. **No** separa dos correcciones seguidas sobre el mismo evento, porque corregir no añade filas al log y el orden siguiente no se mueve entre una y otra. `test/integration/anotador-reclamo.test.ts`.
- **`_lib/equipo-editor.ts` refuses to delete a player who has events.** `partido_eventos.jugador_id` cascades, so removing that person from the roster — from `/mi-equipo/`, by their own captain — would take their events with them and unbalance an already-played match.
- `/anotador/` does **not** use `AdminLayout`: it is used standing on sand, one-handed, in August sun. Its own tokens (`--anot-*`) hang off `body.is-anotador`, it deliberately ignores `prefers-color-scheme` (a dark theme in glare is unreadable) and **there is no offline queue** — replaying one against the `UNIQUE` would produce a cascade of 409s, so with no connection the buttons go dead and say so. A scorer who believes they are saving and is not is worse than one who cannot score.
- **Un punto que cierra un set se pregunta ANTES de mandarse, y ahí está todo.** `anotarPunto` predice con `applyPoint` y, si el parcial cierra, abre el quinto estado de la franja del pulgar (`data-anot-cierre`) en vez de hacer la petición. Cancelar no deja rastro en ninguna parte porque nada llegó a salir: ni evento, ni pliegue, ni `log_version`. El servidor no cambia —para él ese punto sigue cerrando el set— y por eso esto **no** necesitó migración ni tocar `plegarEventos`. La alternativa, dejar el set abierto hasta un evento de cierre, obligaba a meter un tipo nuevo en el `CHECK` de `partido_eventos` (reconstruir la tabla, y con ella el `UNIQUE(partido_id, orden)` y los `ON DELETE CASCADE`) el día antes del torneo.
- **El aviso de punto de set es una pestaña en `absolute` sobre el borde del marcador, no una línea más.** Se calcula simulando el punto con `applyPoint`, no comparando el tanteo con el objetivo: la ventaja mínima también decide y a 20–20 no cierra nadie. En el flujo costaba 24px medidos en 390×844 y se los llevaba el estado de la botonera (870 → 894), que es justo cuando se toca más deprisa; montada encima, `reposo` y `punto de set` miden la franja del pulgar en el mismo 625–775. Lleva el color del equipo que puede cerrar (`--anot-a`/`--anot-b`), y dice «punto de partido» cuando además lo gana.
- **La lista de `/anotador/` enseña la hora, no la pista.** Ponía `pista || hora` y el torneo entero se juega en una sola pista: los treinta partidos decían «Pista central» en el sitio del único dato que los distingue.
- **No se anota por encima del final.** `aplicarPunto` ignora los puntos que llegan con el partido ya decidido, pero la sentencia agregada de estadísticas cuenta **todas** las filas del log: seguir pulsando tras el último punto engordaba la ficha de un jugador sin mover el marcador, y el partido acababa con más puntos repartidos que puntos tuvo. `registrarEvento` lanza `PartidoTerminado`; para tocar un resultado cerrado están deshacer y corregir, que repliegan entero.
- **El cerrojo de `MarcadorSinAdoptar` compara el marcador plano con el pliegue, no mira si el log está vacío.** La condición vieja («sin eventos y con puntos») se saltaba entera por el camino de «soltar»: anotador suelta → el panel corrige a mano → el anotador vuelve a pulsar y el pliegue reescribe las columnas planas llevándose la corrección. La misma pérdida silenciosa, por la otra puerta. Por eso `adoptarMarcador` también acepta un partido que ya tiene log y escribe el `ajuste` **al final**, no en el orden 0: si no, quedaba encerrado entre las dos puertas («anotar» daba 409 y «adoptar» decía «ya tiene anotación»).
- **El saldo de apertura tampoco se deshace.** Borrarlo replegaba un log vacío: el 8–6 adoptado pasaba a 0–0 y, con `origen_marcador` ya en `'eventos'`, no había marcador a mano que volver a ofrecer. Un toque en «Deshacer» y ocho puntos no estaban en ninguna parte. La salida es la misma que para corregirlo: soltar y volver a adoptar.
- **`sincronizarCuadro` en `_lib/torneo.ts` es la vuelta atrás de `propagarResultado`.** Deshacer el punto que cerró una semifinal la devolvía a `live` y le quitaba el ganador, pero la final se quedaba con el finalista ya colocado. `revertirProgresion` sólo vacía huecos marcados `progresion` y sólo si ese cruce sigue `scheduled` — ahí ya hay gente jugando. Lo llaman deshacer, corregir y **adoptar** (adoptar un partido ya ganado a mano también lo deja `finished`: era el cuarto camino al final y el único sin cuadro detrás). Anotar sigue llamando a `propagarResultado` a secas: un punto puede cerrar un partido, nunca abrirlo, y es la ruta que se recorre miles de veces al día.
- **`ErrorDeAnotacion` es lo que el endpoint devuelve con su texto; lo demás es un 500.** Antes cualquier `Error` de menos de 200 caracteres salía como 409 con su mensaje, así que un «D1_ERROR: variable number must be between ?1 and ?100» aterrizaba en el móvil del anotador con pinta de regla del juego. Relacionado: la alineación se acota a `MAXIMO_EN_PISTA`, porque **D1 corta en 100 parámetros** y el `IN (...)` se construye con tantos huecos como ids lleguen.
- **El coste de anotar no puede crecer con lo anotado.** `leerEstado` es **una** consulta (el `LEFT JOIN` de nombres iba aparte, releyendo el log entero) y pliega en **una pasada** con `aplicarEvento` (replegaba el log completo por cada evento: a 250 eventos, ~31.000 pliegues para pintar doce líneas). Y las escrituras pasan su `ResultadoAnotacion` a `respuesta()` en vez de recalcularlo. Medido: de 22→30 ms por punto a 19→22 ms y plano. `test/integration/anotacion-estres.test.ts` lo fija **contando consultas**, no milisegundos.
- **El aviso de error vive pegado a la franja del pulgar, no en la cabecera.** Medido: estaba en y 64–126 con la franja en 598–748 —472px de distancia— en una pantalla cuya premisa es que sólo se mira tres segundos entre punto y punto. Y desde que la pintada optimista se deshace sola al fallar, ese aviso es la **única** señal de que hay que repetir el punto. Va en `position: absolute` sobre el hueco que la franja ya reserva, así que aparecer no mueve un botón. `AnotadorLayout` lo cede con `avisoJuntoAlPulgar`; la lista de partidos no tiene franja y lo conserva arriba.
- **La pintada optimista se deshace cuando la petición falla.** Antes el `catch` llamaba directo a `recargar()`, y sin cobertura ésa fallaba también: la excepción salía por encima del `catch`, el `finally` repintaba el estado **optimista** y el marcador se quedaba con un punto que no existía en ninguna base de datos (más una promesa rechazada sin recoger). Y `api()` en `core.js` traduce la caída de `fetch`: sin eso el aviso decía «Failed to fetch». Esa caída es además lo que enciende la banda de sin conexión — `navigator.onLine` dice que sí enganchado al wifi del chiringuito.
- **El reloj corre en el cliente, con su propio intervalo, y no con el repintado.** En `/directo/` entre dos sondeos pasan tres segundos —sesenta si no hay nadie jugando—, y en `/anotador/` no hay sondeo ninguno: atado al repintado, el reloj sólo avanzaría al anotar un punto. Correrlo aparte no cuesta ni una petición más. `elapsed()` de `match-utils.js` necesita `startedAt` **y** `elapsedMs`, no solo el ancla: con la pausa, `startedAt` vuelve a `NULL` sin que el reloj haya vuelto a cero, y sin el acumulado `elapsed()` devolvería 0 cada vez que se pausa. Por eso `GET /api/anotacion` y `GET /api/directo` mandan los dos campos — a `/api/directo` le faltaba `elapsedMs` y el chip público habría leído mal justo después de la primera pausa de cada partido, aunque `/anotador/` lo pintara bien. Va en su propio `<span>` con `font-variant-numeric: tabular-nums`: los dígitos de Inter no miden lo mismo, y como las dos líneas de detalle van centradas, sin eso la línea entera se desplaza una vez por segundo.
- **El anotador no sondea, pero relee al volver a la pantalla.** Un partido sólo cambia cuando lo toca quien lo anota, así que sondear sería gastar por gastar; pero el móvil se bloquea entre sets, y desde el reclamo también puede haber cambiado de manos mientras tanto: en los dos casos el primer toque se lo lleva un 409 — justo cuando hay tres segundos para anotar.
- **`partido_cambios.tras_orden` puede apuntar a un evento que ya no existe, y quien lo lee tiene que contar con ello.** No es clave ajena a propósito (el punto al que se ancló un cambio se puede deshacer y el cambio siguió ocurriendo), pero `sentenciasSetNumero` buscaba ese orden exacto en un mapa y caía a 1 al no encontrarlo: deshacer el punto del ancla y corregir después cualquier otro —la corrección dispara el recálculo— mandaba un cambio del tercer set al primero **en el historial que ve el público**. Ahora vale el set del último evento que sí sobrevive antes de esa posición. `test/integration/cambios-estres.test.ts`.
- **Anotar exige que el partido esté en directo, y eso lo decide una persona, no el primer punto.** `sentenciasDerivadas` escribe `status = 'live'` en cada pliegue, así que anotar el primer punto **publicaba el partido** —portada, chip de la cabecera y `/directo/`— sin confirmación y sin vuelta atrás desde el anotador. Ahora `registrarEvento` y `adoptarMarcador` lanzan `PartidoNoEnDirecto` (409) si el partido no está `live`; adoptar también, porque escribe por el mismo pliegue y era la otra puerta al mismo agujero. El guardia mira primero si el partido ya está `finished` (lanza `PartidoTerminado`) y sólo después si no está `live`: en el orden contrario un partido terminado decía «no está en directo, ponlo en directo», y seguir ese consejo topaba con «ya ha terminado» — dos avisos que se contradicen, y el primero manda por un camino que el propio servidor rechaza. `moverCronometro` comparte el mismo orden por la misma razón. Lo que **no** se bloquea: deshacer, corregir y recalcular (reparan un log que sólo pudo existir estando en directo) y fijar la alineación, que es la preparación previa al pitido. Publicar es `POST /api/anotacion {accion:"directo"}`, con el permiso que ya había (`partidos.anotar`), y en pantalla lleva doble confirmación en **un** diálogo con una fila que hay que marcar: dos diálogos seguidos en un móvil al sol se despachan a ciegas.
- **Fuera de directo, la pantalla no pinta la pista: ocupa su sitio con la decisión de publicar.** Mismo patrón que `pendienteDeAdoptar` — no se pintan botones que van a responder 409. La condición es `status === "scheduled"`, no `status !== "live"`: con `!==` un partido ya `finished` también perdía la pista y se le ofrecía un botón de publicar que el servidor iba a rechazar igualmente.
- **El cronómetro no añadió columnas: reinterpreta las de la migración 0003.** `started_at` es el inicio del **tramo en curso** (`NULL` = parado) y `elapsed_ms` el acumulado de los tramos ya cerrados — que es exactamente lo que `elapsed()` de `match-utils.js` ya calculaba. Tres estados sin nada más: sin estrenar (`NULL` y 0), corriendo (fecha), pausado (`NULL` y > 0). `POST /api/anotacion {accion:"cronometro", marcha}` es idempotente en los dos sentidos: arrancar un reloj que ya corre movería el ancla y regalaría el tramo transcurrido; pausar uno ya parado sumaría el mismo tramo dos veces. Las dos escrituras suben `log_version`. De paso se arregló `sentenciasDerivadas`, que al cerrar el partido hacía `ahora − started_at` y **tiraba `elapsed_ms`**: no se notaba porque nada lo escribía antes de que existiera la pausa, así que con ella cada partido parado entre sets habría reportado sólo su último tramo. `elapsedOnFinish` de `functions/api/partidos.ts` siempre lo hizo bien — eran dos copias de la misma cuenta y una mentía. `action: "start"` de ese mismo fichero se queda como estaba a propósito: el panel sigue fijando `live` y `started_at` a la vez, que es su prerrogativa.
- **El cerrojo de publicar es de servidor; el del reloj sin estrenar, de cliente — a propósito, porque protegen daños de tamaño distinto.** Publicar sin querer se ve desde fuera (portada, chip, `/directo/`) y no hay vuelta atrás desde el anotador, así que su guardia está donde una URL no la puede saltar. Anotar con el reloj sin estrenar sólo deja mal una duración, y un 409 más sería otra forma de que la franja del pulgar se quede muerta a pie de pista. Por eso sólo el **estreno** bloquea el punto en pantalla —confirmar el diálogo arranca el reloj y anota el punto que lo abrió, porque un toque descartado al borde de la pista es un punto perdido, y si arrancar el reloj falla el punto no se envía—; la pausa nunca bloquea, porque está para el descanso entre sets y un toque que no hace nada es justo la trampa que esta pantalla no se puede permitir. El reloj se pinta arriba del panel, lejos del pulgar: un control de pausa cerca de la zona de anotar se pulsaría por accidente.
- **El aviso de error tenía un único hueco, y ese hueco vivía escondido justo en los estados que fallan.** `[data-anot-error]` colgaba de `[data-anot-pulgar]`, que se oculta exactamente en los estados con botones que pueden responder 409 (fuera de directo, decisión de adoptar, relevo de otra persona): un fallo ahí no decía nada. Ahora hay un hueco por bloque (`[data-anot-error-fuera]`, `[data-anot-error-decision]`, `[data-anot-error-relevo]`) y `estadoBloque()`/`mostrarError()` en `partido.js` mandan el mensaje al que esté en pantalla — lo que de paso arregló el mismo agujero, ya existente, en adoptar y en «Empezar en 0–0». El hueco del pulgar en sí no se movió: su sitio ya estaba medido y probado. El relevo llegó con su propio mecanismo para esto —mover `[data-anot-error]` entero a un `data-anot-error-destino` compartido—, pero un hueco por bloque ya cubría el mismo problema para `fuera`/`decidir`; se descartó tener las dos soluciones a la vez y `relevo` se sumó al primer patrón en vez de generalizar el segundo.

## RBAC (roles y permisos)

- **The permission catalogue lives in code**, in [functions/_lib/permisos.ts](functions/_lib/permisos.ts), as `recurso.accion` strings (`equipos.editar`, `usuarios.ver_como`…). What lives in the database is only the *assignment*: `rol_permisos` (which permissions a role grants) and `usuarios.rol_id` (which role an account has). A typo in an endpoint is then a compile error, not a 403 in production.
- **The `admin` role is `es_sistema = 1`, holds no `rol_permisos` rows at all, and its permissions are implicit and total.** This is the anti-lockout design, not an optimisation: if they were materialised, an admin could untick `roles.editar` on their own role and leave the system with nobody able to hand out permissions. `/api/admin/roles` refuses to edit or delete it.
- The seed in [db/migrations/0013_roles.sql](db/migrations/0013_roles.sql) repeats `ROLES_SISTEMA` by hand, because a migration can't import from `functions/`. `test/unit/paridad-permisos.test.ts` is what makes "keep them in sync" enforceable. Note that workerd's SQLite caps compound `SELECT`s far lower than desktop SQLite: the seed is one `INSERT … VALUES`, not a chain of `UNION ALL`.
- **`is_admin` is gone**, dropped by [db/migrations/0022_fuera_is_admin.sql](db/migrations/0022_fuera_is_admin.sql) one release after the code stopped reading it. It could not go in the same release as the RBAC code: migrations are applied *before* the new code ships, so the old code — still serving traffic — would have run `SELECT is_admin` in `requireAdmin` and, worse, in `getAuthContext`, which holds up `/api/me` for everyone. The one-way mirror `/admin/usuarios/` kept on the column went with it. Note for any future column drop: **SQLite refuses to drop an indexed column**, so `idx_usuarios_is_admin` (migration 0005) had to fall first, and it goes first in the file for a second reason too — `DROP INDEX IF EXISTS` can be re-run and `DROP COLUMN` cannot.
- `GET /api/me` exposes `acceso` (role + effective permission list) and `auth.js` puts it in `CopaAuth.state.acceso`; `CopaAdmin.puede(permiso)` and `[data-permiso]` use it to hide sidebar entries and buttons. **That is for painting, never for authorising** — the real gate is `requirePermiso` on every endpoint.
- **Mi zona's shortcut to the tools is built in JavaScript, not marked up.** `/mi-equipo/` offered no path to `/admin/` or `/anotador/`: both were reachable only by typing the URL, and the scorer is the tournament-day tool. [public/assets/herramientas.js](public/assets/herramientas.js) inserts the bubble after the hero **only** once `/api/me` confirms the permission, so `mi-equipo.astro` carries neither URL and an account with no role sees nothing — not on screen and not in view-source, which is what was asked for. The panel link is gated on `panel.entrar`; the scorer link on `partidos.anotar` **or** `partidos.editar`, a hand copy of the `requireAlgunPermiso` in [functions/api/anotacion.ts](functions/api/anotacion.ts) — Organización holds `partidos.editar`, so the link never promises a screen that answers 403. `test/unit/mi-zona-herramientas.test.ts` guards the invisibility *and* that copy.
- **That bubble carries neither `.paso` nor `.reveal`, and both omissions are load-bearing.** `.paso:nth-child()` hands out the colour, the tilt and the side the tail points to **by position**, and this one is inserted by a script, so its index among its siblings would decide how it paints; `.zona-herramientas` sets all three itself. And `site-interactions.js` queries `.reveal` once at load and unobserves on first sight, so a node inserted afterwards would never get `in-view` and would sit at `opacity: 0` for ever. The sello holds the role name instead of a number: there is no sequence here to number, and saying which hat you are wearing is what explains the buttons.

## Frontend changes

- When a request involves changes to the web frontend (UI, layout, styling, visual components), ALWAYS invoke the `frontend-design:frontend-design` skill before implementing.
- Every frontend change MUST be responsive and adapt to the device/viewport size. Always verify and style the mobile browser (phone) version, not just desktop — use the existing media queries in [src/styles/global.css](src/styles/global.css) (breakpoints 900px and 560px) or add new ones as needed.
- The base values in global.css are the **mobile** scale. Desktop density lives in a single `@media (min-width: 901px)` block (start of the media-queries section): it compacts type and vertical rhythm (~0.8x) so more fits on screen at 100% zoom. When adding a new desktop-visible component, check whether it needs an entry there too.
- **A rule in this block can be silently overridden by a later one at the same specificity, and nothing says so.** A later rule wins a specificity tie whether or not the earlier one sits inside a media query — appending CSS near the end of the file can kill a desktop override written months earlier, and only the properties **both** rules declare go dark, which is what makes it hard to spot. Known instances: `.header-directo`, `.header-directo.is-vivo` and `.directo-aviso` are fully shadowed by unconditional twins later in the file (the desktop density never reaches the chip, which renders at mobile scale on desktop too); `.nav-drop > summary` is only partially shadowed — its later twin redeclares `padding` but not `font-size`, so only the padding is dead. All pre-existing, out of scope for this branch. When adding a rule near the end of `global.css`, check whether the same selector already appears inside the desktop block: the new rule will win.
- Note when verifying with headless Chrome screenshots: Chrome clamps the window to a ~500px minimum width, so `--window-size=390,...` renders a 500px layout cropped to 390 — right-edge "cuts" at mobile sizes are usually this artifact, not a layout bug.

## Tests

Vitest, with three projects declared in [vitest.config.ts](vitest.config.ts). Each has its own config under `test/<proyecto>/vitest.config.ts`.

| Project | Runs in | Covers | Needs a build |
|---|---|---|---|
| `unit` | Node (jsdom per file via `// @vitest-environment jsdom`) | Pure logic (`validacion`, `nombres`, `_lib/admin` helpers) and the client scripts in `public/assets/` | No |
| `integration` | workerd, with **real D1 and R2** (migrations applied) | Handlers from `functions/` imported directly and called with a fabricated context | No |
| `e2e` | Same, plus `main = .worker/index.js` and `SELF.fetch` | **Route wiring only** — that `_middleware.ts` really runs in front of every route | Yes |

- **Write behaviour tests in `integration`, not `e2e`.** `e2e` exists for one thing: proving the middleware is actually wired. Calling handlers one by one can never show that.
- Seed with the helpers in [test/helpers/db.ts](test/helpers/db.ts) (`crearUsuario`, `crearAdmin`, `crearEquipo`, `sembrarFoto`, `peticion`) — no loose SQL in test files. Session and «ver como» cookies are signed with the real `createSessionCookie` / `createVerComoCookie` against the test `SESSION_SECRET`; never hand-roll a cookie.
- Call a handler with `ctx(request, env)` from [test/helpers/ctx.ts](test/helpers/ctx.ts). Use `crearContexto` instead when you need to assert whether `next` was called (that's how the middleware tests prove a request was cut off rather than merely rejected downstream).
- **Nothing resets state on its own.** `isolatedStorage` disappeared in `@cloudflare/vitest-pool-workers` 0.18, so [test/integration/setup.ts](test/integration/setup.ts) empties every table and the R2 bucket in an `afterEach` and re-seeds the current edición, the live-scoring `ajustes` **and the system roles** (derived from `ROLES_SISTEMA`, not copied by hand). Add any new table to its `TABLAS` list, or tests will leak into each other — the UNIQUE indexes on `equipos`/`jugadores` are global and will start failing depending on test order. If a table is wiped but not re-seeded, the damage is worse than leakage: drop `roles` without re-seeding and every `crearAdmin` in the suite starts producing 403.
- `crearAdmin` in [test/helpers/db.ts](test/helpers/db.ts) is the leverage point for anything touching authorisation: ~40 tests open the panel through it, and none of them should know how permissions are stored. Use `crearUsuarioConPermisos([...])` for a reduced role and `asignarRol(id, clave | null)` to grant or revoke mid-test.
- Test files are excluded from the root `tsconfig.json` (they import `cloudflare:test`, which `astro check` knows nothing about). They are type-checked separately by `npm run test:types` against [test/tsconfig.json](test/tsconfig.json). A binding added to the miniflare config also needs an entry in [test/env.d.ts](test/env.d.ts).
- `paridad-validacion.test.ts` compares the shared literals of `functions/_lib/validacion.ts` and `public/assets/team-form.js`. If you change a validation rule, change both — that test is what makes the "keep them in sync" rule enforceable instead of aspirational.
- **`integration` runs with `testTimeout: 20000`, not Vitest's default 5 s.** Each test boots workerd, applies migrations and talks to a real D1; the heavy ones in `anotacion` and `torneo-admin` (scoring a match point by point, generating a whole league) take ~7 s alone and over 15 s under parallel load, so with the default they passed or failed depending on how busy the machine was. A test that now reaches 20 s is genuinely broken, not slow.

### Before merging a branch into `development`

1. Add or update tests for everything the branch touches. Any new endpoint or `_lib/` function arrives with its tests.
2. Re-read the existing tests of the areas affected and update the ones the change invalidates — a test that had to be weakened to keep passing is a finding, not a chore.
3. Run `npm run verify`. Do not merge with anything red — `npm run integrar` runs it for you and stops there if it isn't green.

## Git workflow (Git Flow, with several sessions at once)

- **Three commands do all of this, and they exist because the recipes by hand are what collide.** `npm run rama -- feature/x` opens the branch and its worktree; `npm run integrar -- -m "…"` publishes it to `development`; `npm run ramas:limpiar` reports what is left over (`--aplicar` to act on it). What follows is what they do and why.
- This repo follows **Git Flow**. `main` only ever receives merges from `development` — never commit or push directly to `main`.
- `development` is the integration branch and the base/target for all work. Every branch below is cut **from `development`** and merged **back into `development`** via PR/merge, never straight into `main`:
  - `feature/<nombre-corto>` — new functionality or enhancements.
  - `bugfix/<nombre-corto>` — non-urgent bug fixes found on `development`.
  - `release/<version>` — stabilizes `development` for a release (version bump, final polish) before it goes to `main`.
  - `hotfix/<nombre-corto>` — urgent fix branched from `main` to patch production, merged back into **both** `main` and `development`.

### The two invariants

1. **A branch is checked out in exactly one place, and that is the only lock there is.** `git worktree add` failing with «already used by worktree at …» is not an obstacle to route around: it is another session saying it is busy. Never `--force` past it. The same refusal is what serialises a promotion, because `.worktrees/promote-main` can only exist once.
2. **The main checkout is nobody's workspace, and that includes its git state.** No session runs `checkout`, `merge`, `rebase`, `reset` or `branch -d` there. Two agents (or two terminals) sharing it switch branches out from under each other: a `checkout` in one makes the other's files vanish mid-edit, and uncommitted work can be lost outright. This has already happened here. The **one** allowed command is `git -C <principal> pull --ff-only` — clean tree, fast-forward only, so it cannot lose anything — which is what `npm run integrar` runs at the end to keep its view current. On `index.lock`, another session is doing the same: wait and retry, never delete the lock.

### Starting work

```bash
npm run rama -- feature/<nombre-corto>     # o bugfix/…, release/…, hotfix/…
cd .worktrees/<nombre-corto>
```

By hand it is `git fetch origin`, then `git worktree add .worktrees/<n> -b feature/<n> origin/development`, then `npm install` **inside the worktree**. The branch is cut from **`origin/development`**, never by checking `development` out — the old recipe here did `git checkout development && git pull` in the shared checkout, which is precisely what two sessions starting at the same time collide on. The `npm install` is not optional: `node_modules/` does not travel with a worktree. A `hotfix/` is cut from `origin/main`, because it patches what production is running.

Worktrees go under `.worktrees/` (gitignored), **not** in sibling directories, so the cleanup tooling finds them. A `.claude/worktrees/<nombre-aleatorio>` with a detached HEAD on a `claude/*` branch is what the built-in worktree tool creates; it sidesteps every convention here — location, branch name, cleanup — so don't use it.

### Publishing to `development`

```bash
npm run integrar -- -m "qué aporta la rama"
```

Merge `development` into the branch, verify, push the branch, then the merge commit — in that order, and **`development` is never checked out anywhere**:

```bash
git fetch origin && git merge origin/development   # los conflictos se resuelven AQUÍ, donde son tuyos
npm run verify                                    # verde DESPUÉS de ese merge, no antes
git push -u origin feature/<x>
git worktree add --detach .worktrees/_merge-<x> origin/development
git -C .worktrees/_merge-<x> merge --no-ff feature/<x> -m "Merge feature/<x> into development: …"
git -C .worktrees/_merge-<x> push origin HEAD:development
git worktree remove .worktrees/_merge-<x>
```

A **detached** worktree does not claim the branch, so this works while the main checkout sits on `development`. If the push comes back rejected as non-fast-forward, another session integrated while verify was running: the whole cycle repeats — merge again, **verify again** — because publishing a combination nobody verified is what all of this exists to prevent. There is no `push --force`, ever.

This does not require asking first. What it does require is verify green and tests for what the branch changed (see Tests above).

### Migrations with several branches open

`db/migrations/` carries two `0003_` and two `0022_` because two sessions each took "the next number", and the order migrations apply in is the difference between a deploy and a downed login. `npm run rama` prints the number that is free; `npm run integrar` **refuses to merge** when a number in your branch also exists in `development` under a different filename. That check runs *before* the merge — afterwards both files coexist and the duplicate is already in. Renumber **yours**, never one already applied in production.

### Ports, servers and shared side effects

- `npm run rama` assigns a **slot**: worktree N runs on `4321+10N` / `8788+10N`, and the port always goes on the command line (`npm run dev -- --port 4331`, `npx wrangler dev --port 8798`). Slot 0 is the main checkout's pair, the one `.claude/launch.json` fixes — and the preview pane reads *that* file, not the worktree's copy. The assignment lives in `.git/copa-slots.json`.
- Local D1/R2 live in each worktree's own `.wrangler/state`, so they are already isolated. A busy port is a stale `workerd` from another session, not a bug in the code.
- **Don't run `npm run verify` in two worktrees at once.** Each boots workerd and a real D1, and that parallel load is exactly what pushes the `integration` project past its 20 s timeout (see Tests).
- `npm run db:status` and `npm run db:migrate` are `--remote`: they hit **production** from any worktree. Promotion only, one session.

### Finishing

```bash
npm run ramas:limpiar               # informa
npm run ramas:limpiar -- --aplicar  # retira worktrees y ramas ya integradas
```

It never retires the main checkout, the worktree you are in, one with uncommitted changes, or a branch that is not integrated — **another session's worktree can be alive even when its branch is already merged**, so it reports instead of guessing. By hand the order matters: `git worktree remove` **before** `git branch -d`, because git refuses to delete a branch that is still checked out somewhere. And never `rm -rf` a worktree: what is left is a directory git does not know, and any git command run inside it walks up and operates **on the main checkout** — `.worktrees/publica` was exactly that.

### Promoting to `main` — its own ceremony, and you ask first

- **Never push to `main` or merge `development` → `main` without asking first.** When work is ready to promote, stop and: (1) give a summary of the changes being promoted, (2) name the migrations production is missing (`npm run db:status`), (3) ask for explicit confirmation before merging `development` into `main` and pushing.
- **Promoting to `main` *is* applying the migrations. Always, in every flow, no exceptions.** A deploy ships code, not schema. `main` is what production runs, so the moment `development` lands on `main`, production's D1 has to be at the same migration as the branch — otherwise the new code queries tables that do not exist. This has already taken the site down: the promotion carrying RBAC + torneo + directo shipped code needing 0013–0021 against a database stuck at 0012, and what broke was **login itself**, because `permisosDeUsuario` joins `roles`. Once the promotion is confirmed, it is these steps in this order:

  ```bash
  git fetch origin
  git worktree add .worktrees/promote-main main   # si git se niega, otra sesión está promoviendo
  npm run db:status                               # what production is missing
  npm run db:migrate                              # apply it — BEFORE the code ships
  git -C .worktrees/promote-main merge origin/development
  git -C .worktrees/promote-main push origin main
  npm run db:status                               # must say "No migrations to apply!"
  git worktree remove .worktrees/promote-main
  ```

  It goes in a worktree of its own, and **its existence is the lock**: `main` can only be checked out in one place, so a second session trying to promote is refused instead of racing. Remove it when done — while it exists, `git checkout main` fails everywhere else. And check `git log origin/main..main` before anything: **a local `main` ahead of `origin/main` is a promotion that was merged and never pushed**, so production is running the old code with nothing saying so. `npm run ramas:limpiar` refuses to retire that worktree for exactly this reason.

  Migrations go **first** so that during the seconds the deploy takes, the old code still serving traffic meets a schema that is a *superset* of what it knows. That is why migrations are additive by default (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN`, `INSERT OR IGNORE`), and it is exactly what a **destructive** migration gives up: for those seconds the schema is a *subset*, so anything the live code still touches breaks. Hence the rule that pays for it — drop a column only a full release after the code stops using it, which is why `is_admin` survived 0013–0021 and only fell in 0022.
- **`predeploy:worker` is a safety net, not the mechanism — never assume it ran.** It only fires if Cloudflare Workers Builds' *Deploy command* is `npm run deploy:worker`; with the default `npx wrangler deploy`, npm never runs the hook and the migrations are skipped in silence, deploy green. The closing `npm run db:status` above is what turns that silence into an answer.
